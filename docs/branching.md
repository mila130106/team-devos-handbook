# Конвенції гілок і комітів

Цей документ визначає правила іменування гілок, оформлення комітів та управління історією у командному проєкті.

## 1. Конвенція іменування гілок
Назви гілок мають бути інформативними та формуватися за шаблоном:
`тип/опис-прізвище`

Основні типи гілок:
* `feature/` — для розробки нових функцій або додавання нових документів (наприклад, `feature/melaniya-docs`).
* `bugfix/` — для виправлення помилок або недоліків.
* `docs/` — для оновлення виключно документації.

## 2. Формат повідомлень комітів (Conventional Commits)
Кожне повідомлення коміту має починатися з префікса, який вказує на характер змін:
* `feat:` — додавання нової функціональності чи розділу.
* `fix:` — виправлення помилки.
* `docs:` — зміни у документації (файли у папці `docs/` або README).
* `style:` — форматування коду, відступи (без зміни логіки).

*Приклад правильного коміту:* `docs: add branching and editor-config guidelines`

## 3. Робота з комітами перед злиттям (Merge)
* Перед створенням Pull Request переконайтеся, що ваш код чи текст працює локально та не містить конфліктів із гілкою `main`.
* Заборонено робити прямі коміти у головну гілку `main` (захист забезпечується правилами Ruleset). Усі зміни проходять через стадію Pull Request із обов'язковим рецензуванням.
* * Зведення комітів (Squash): Усі дрібні проміжні робочі коміти (наприклад, wip, fix typo, try again) обов'язково потрібно зводити в один змістовний коміт перед злиттям гілки у `main` (через git rebase -i або кнопку "Squash and merge" на GitHub). Це забезпечує чисту історію основної гілки.
